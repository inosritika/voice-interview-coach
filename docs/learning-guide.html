1. The big picture: what is a voice agent?

A voice agent is a program you talk to and that talks back — no typing, no reading. Ours plays a job interviewer: you paste a job description and your resume, then answer its questions out loud, and it follows up like a real interviewer would.

Under the hood, "talking to a computer" decomposes into three fundamental conversions, because the AI models that reason well (large language models) only understand text:

  1. Your speech → text (so the model can read what you said)
  2. Text → the model's reply text (the actual "thinking")
  3. Reply text → speech (so you can hear the answer)

Why this decomposition matters: almost every hard problem in voice AI lives between these conversions, not inside them. When has the person stopped talking? How do you avoid a 3-second awkward silence? What happens when the user interrupts? Those are the problems this project exists to teach — the conversions themselves are mostly solved by off-the-shelf models.

2. The two ways to build one

Why build the harder one first? Because the goal of this project is learning, and architecture B teaches you almost nothing — you send audio, you get audio, the interesting parts are invisible. Architecture A forces you to personally solve endpointing, latency, and interruptions. Then, when you swap in B at the end (step 6), you'll be able to say exactly what you gave up — from experience, not from a blog post.

In step 1 we built the STT → LLM → TTS core of pipeline A, with your thumb on the button doing VAD and Endpoint's job: holding = "this is speech", releasing = "I'm done". Since then the thumb has been fully replaced with software — VAD + endpointing (step 2), streaming (step 3), barge-in (step 4) and the debrief (step 5) are all built and working. Part II (§13 onward) walks through each. The diagram above, including its barge-in loop, is now a literal description of the running code.

3. Glossary — every term, with examples

Grouped roughly in the order you'd meet them following one sentence you speak through the system.

Capturing sound

Microphone capture / getUserMedia browser

The browser API that asks the user for microphone permission and returns a live audio stream. The browser is the only practical, cross-platform way for our app to reach a mic — which is why this project needs a web frontend at all, even though it's a "backend-flavored" project.

Example: the permission popup you saw when you clicked Start interview — that was getUserMedia({ audio: true }) executing.

MediaRecorder browser

A browser API that records an audio stream into compressed chunks. You start it, it accumulates data, you stop it, you get a file-like blob.

Example: in our app, pressing the talk button calls mediaRecorder.start(), releasing calls .stop(), and the collected chunks become one clip sent to the server.

Audio formats: WebM/Opus vs WAV/PCM audio

Opus is a modern compressed audio codec (like MP3 but better for speech); WebM is the container file that holds it. PCM is raw, uncompressed samples — just numbers describing the sound wave; WAV is PCM with a small header on top. Compressed is small but must be decoded; raw is big but instantly usable.

Example in our app: uploads are WebM/Opus (a 10-second answer ≈ 80 KB — cheap to send), downloads are WAV (the reply you heard was ~500 KB — but the browser can play it with zero decoding work). Choosing per-direction like this is a classic bandwidth-vs-simplicity tradeoff.

Sample rate audio

How many times per second the sound wave is measured, in hertz. More samples = higher fidelity = more data. Speech models don't need music-grade fidelity.

Example: music CDs use 44,100 Hz. Whisper listens at 16,000 Hz; our piper voice speaks at 22,050 Hz. Telephone audio is 8,000 Hz — which is why phone calls sound "thin".

Understanding speech

STT — speech-to-text (also called ASR) pipeline stage

A model that converts audio of speech into written text. Also called ASR (automatic speech recognition). Ours is faster-whisper, an optimized version of OpenAI's open-source Whisper model, running on your CPU.

Example: our smoke test fed piper's audio of "The quick brown fox jumps over the lazy dog" into whisper, and got exactly that sentence back as text.

Beam search how models decode

When transcribing, the model considers several candidate transcriptions in parallel ("beams") instead of greedily committing to the single most likely word at each step, then keeps the best overall sentence. Slower but more accurate.

Example: hearing "I worked at a fin-tech…", a greedy decoder might lock in "fin" then be stuck with "fin tech"; beam search keeps both "fintech" and "fin tech" alive until more audio disambiguates. Our code passes beam_size=5 — five candidates.

VAD — voice activity detection step 2 ✓ built

A tiny, fast model that looks at ~30-millisecond slices of audio and answers one question per slice: is this speech, or not? It knows nothing about words or meaning — it's purely a sound-vs-silence gatekeeper. The standard choice is Silero VAD, which beats naive "is the volume loud?" checks (those get fooled by keyboard clatter and coughs).

Example: while you answer a question, VAD emits a stream like speech, speech, speech, silence, silence, speech… — the raw signal that endpointing (below) interprets. In our app this is now real: backend/vad/silero.py scores every 32 ms slice of mic audio with a probability, all interview long. Details in §13.

Endpointing / turn detection step 2 ✓ built

The decision "the speaker is finished", as opposed to "the speaker is pausing to think". It consumes VAD's silence stream (e.g. "500ms of continuous silence") and, done well, also looks at the transcript so far. This is widely considered the hardest UX problem in voice agents.

Example: you say "My biggest achievement was… [1.5s pause, thinking] …leading the payments migration." A naive 700ms-of-silence rule guillotines you mid-thought and the agent answers half a story. But a 2-second rule makes every single exchange feel laggy. Semantic endpointing checks whether "My biggest achievement was" even sounds like a finished sentence (it doesn't — so wait longer). We built the classic fixed-silence baseline (700 ms) in backend/endpointing.py — deliberately the naive version, so you can feel its failure modes yourself. §13 dissects it.

Thinking

LLM — large language model pipeline stage

The model that actually converses — reads the transcript, decides what the interviewer should say next. Ours is Llama 3 8B running locally via Ollama. LLMs read and write only text, which is the entire reason STT and TTS must exist around it.

Example: given your answer "I led a team of five", the LLM (prompted to be a rigorous interviewer) produces "What was the hardest people-problem you faced with that team?"

Token llm

The unit LLMs read and write — roughly ¾ of a word. Models generate one token at a time, which is why replies can be streamed word-by-word (see streaming, below).

Example: "interviewing" might be split into the tokens inter + view + ing. A 100-word answer is roughly 130 tokens.

Context window llm

The maximum amount of text (in tokens) an LLM can consider at once — its working memory. Everything must fit: the system prompt, the whole conversation so far, and the reply being generated.

Example: llama3:8b has an 8,192-token window ≈ 6,000 words. A long interview (JD + resume + 30 exchanges) can exceed it — and Ollama silently drops the oldest text, which is our system prompt. The interviewer would literally forget what job it's hiring for. This is a known rough edge in our current code (see §12).

Stateless model / conversation history llm

LLMs remember nothing between calls. The illusion of memory is created by re-sending the entire conversation every single turn.

Example: on turn 10 of your interview, main.py sends all 9 previous exchanges plus your new answer. The model re-reads everything, every time. This is why main.py keeps the messages list — it, not the model, is the memory.

System prompt llm

A special first message that sets the model's role, rules, and knowledge for the whole conversation. The user never sees it.

Example: ours (in backend/prompts.py) says: be a warm-but-rigorous behavioral interviewer, ask ONE question at a time, keep turns to 1–3 sentences, no markdown or emoji because your words will be spoken aloud by TTS, probe vague answers using STAR (Situation, Task, Action, Result) — and then embeds your pasted JD and resume so questions are role-specific. Writing prompts "for the ear" is a real voice-AI discipline: a TTS engine will cheerfully read **asterisk asterisk** out loud.

Speaking

TTS — text-to-speech pipeline stage

A model that converts written text into spoken audio. Ours is piper, a fast local neural TTS.

Example: the interviewer's greeting you heard in our test — "Welcome to the mock job interview…" — was piper converting the LLM's text into a 505 KB WAV file in about a second.

Phoneme tts internals

The smallest unit of spoken sound. TTS engines first convert text into phonemes (using pronunciation rules), then render phonemes as audio. This two-step split is why TTS can pronounce words it has never seen.

Example: "coach" becomes the phonemes k-oʊ-tʃ. Piper uses a library called espeak-ng for this step. It's also why TTS sometimes mispronounces names: "Ritika" gets whatever phonemes the rules guess.

Vocoder / neural voice tts internals

The neural network that turns phonemes into an actual sound wave — the part that makes it sound like a human rather than a 1990s robot. This is the 60 MB .onnx file we downloaded.

Example: en_US-lessac-medium.onnx is one specific voice (trained on one speaker's recordings). Swap the file, swap the voice — same text, different person.

Moving data around

HTTP vs WebSocket transport

HTTP is like sending letters: the browser asks, the server answers, the exchange is over. The server can never speak first. A WebSocket is like a phone call: one connection stays open and either side can send anything at any time.

Example why this matters for voice: mid-turn, our server pushes "status: thinking" to the browser without being asked — impossible over plain HTTP. Later it gets more critical: streaming partial transcripts (step 3) and "user interrupted, stop the audio NOW" (step 4) both need server-initiated push. That's why we used a WebSocket from day one even though step 1 barely needs it — re-architecting the connection layer mid-project would be painful.

Text frames vs binary frames transport

A WebSocket can carry two kinds of messages. We use a simple convention: text frames are JSON control messages (with a type field), binary frames are always audio. This is exactly how production voice platforms structure their protocols.

Example — one full turn on the wire:
→ you send: <binary: 80KB WebM clip>
← server: {"type":"status","text":"transcribing"}
← server: {"type":"transcript","text":"I led a team of five"}
← server: {"type":"status","text":"thinking"}
← server: {"type":"reply","text":"What was the hardest…"}
← server: <binary: 500KB WAV audio>

Software design

Adapter pattern (a.k.a. ports & adapters) design pattern

Define an abstract interface for a capability ("anything with a transcribe() method is an STT engine"), write multiple interchangeable implementations of it, and make the rest of the code depend only on the interface. Swapping implementations then requires zero changes to the code that uses them.

Example from our code: 
class STTEngine(ABC):                      # the interface (stt/base.py)
    async def transcribe(self, audio: bytes) -> str: ...

class LocalWhisperSTT(STTEngine): ...      # implementation 1 (local)
class DeepgramSTT(STTEngine): ...          # implementation 2 (hosted API)

# main.py only ever writes:
text = await engines.get_stt().transcribe(audio)   # doesn't know which!
Setting STT_ENGINE=deepgram in .env swaps whisper for Deepgram with no code change. Every stage (STT, LLM, TTS) follows this pattern — and it's what will make step 6's realtime-model swap a component replacement instead of a rewrite.

Factory design pattern

The single place that knows how to construct the right concrete object for the current configuration. Keeping construction in one spot means only one file ever imports the concrete engines.

Example: backend/engines.py — get_stt() reads the flag, builds LocalWhisperSTT or DeepgramSTT once, caches it, and hands it out forever after.

Event loop, blocking, and asyncio.to_thread python async

Our server runs on an event loop: one thread juggling many waiting tasks (network reads, timers) by switching between them whenever one is idle. This works only if no task hogs the thread. Heavy CPU work like running a neural network blocks — hogs the loop so nothing else can happen, not even receiving a WebSocket message. asyncio.to_thread(...) pushes such work onto a separate thread so the loop stays free.

The analogy that makes it click: the server is one waiter serving a whole restaurant. It handles every connected client with a single thread — which works because a voice server spends almost all its time waiting (for the next audio chunk, for Ollama to reply), and waiting isn't work. The instant a task starts waiting, the loop sets it aside and serves someone else; it comes back when the wait is over. One waiter looks like ten, because no customer needs the waiter while the kitchen is cooking — only to place an order or receive the food. The word that marks a "safe to switch away" point is await.

Blocking is the one thing that breaks the trick. The scheme depends on tasks genuinely waiting (idle). But running a neural network isn't waiting — it's the CPU grinding flat-out for ~2 seconds, with no idle moment to slip away. It's the waiter deciding to personally cook one table's meal at the table: for those 2 seconds every other table is frozen, unable to even place an order. That's the top timeline below.

asyncio.to_thread is hiring a line cook. It hands the heavy work to a background thread (a cook in the kitchen) and awaits the result — so from the loop's view it's back to normal "waiting" and free to serve other clients. Whisper still takes its 2 seconds, but now in parallel, on the worker thread. That's the bottom timeline.

In our code (stt/local_whisper.py) — note the inner function is a plain, non-async function, because whisper has no await points to exploit, so it must go to a thread:

async def transcribe(self, audio_bytes: bytes) -> str:
    # to_thread ships the blocking work to a worker; the loop stays free.
    return await asyncio.to_thread(self._transcribe_sync, audio_bytes)

def _transcribe_sync(self, audio_bytes: bytes) -> str:
    segments, _ = self._get_model().transcribe(...)   # heavy, blocking
    return " ".join(...)
Why it matters more later: freezing for 2s is merely rude to other users today. But in step 4 (barge-in) the server must listen for you interrupting while it's speaking — two things at once. A blocking call that freezes the loop means it literally cannot hear your interruption. Keeping the loop free stops being a nicety and becomes the thing that makes the feature possible. (Piper in tts/local_piper.py is wrapped the same way, for the same reason.)

Environment variables and .env configuration

Configuration passed to a program from outside, instead of hardcoded in it. A .env file holds them for local development; the python-dotenv library loads it at startup. Secrets (API keys) live here so they never get committed to git.

Example: our .env contains LLM_ENGINE=local and OLLAMA_MODEL=llama3:8b. Change a line, restart, different brain — code untouched.

The concepts of steps 3–5 (all built now — Part II has the deep dives)

Streaming step 3 ✓ built

Processing data while it's still arriving instead of waiting for the whole thing. Applied to every stage: STT emits partial transcripts while you're still talking; the LLM emits tokens as it thinks; TTS starts speaking the first sentence before the LLM has finished the last.

Example: our step-1 pipeline was fully sequential — STT 1s + LLM 2s + TTS 1s = 4s of silence. After step 3 the LLM's token stream is cut into speakable clauses and each is synthesized and played while the rest is still generating — measured time-to-first-audio dropped from ~5.5s to ~2.75s. Same total work — radically different feel. §14 shows exactly how.

Barge-in step 4 ✓ built

Interrupting the agent mid-sentence, like you would a human: it should stop talking immediately and listen.

Example: the interviewer starts a long question, you cut in with "sorry, could you repeat the last part?" — playback halts and it listens. This forced real concurrency into the server (each turn is now a cancellable task) and produced the two most instructive bugs of the whole project — §15 tells both war stories.

Echo cancellation step 4 ✓ built

Removing the agent's own voice (coming out of your speakers) from what the microphone hears. Without it, the agent hears itself, its VAD says "speech!", and it interrupts itself, forever.

Example: you know this bug from bad conference-call setups where you hear your own voice echoed back. Browsers ship an echo canceller (echoCancellation: true on getUserMedia) — one reason capturing audio in the browser is a gift.

Floor state step 2/4 ✓ built

An explicit variable tracking who has permission to speak right now — borrowed from linguistics ("holding the floor"). Sounds trivial; prevents chaos.

Example: states like USER_SPEAKING → AGENT_THINKING → AGENT_SPEAKING → USER_SPEAKING. Barge-in is then a clean rule: "if VAD detects speech while state is AGENT_SPEAKING → kill playback, set state to USER_SPEAKING." Without the explicit state, you get two parties talking over each other in an infinite loop.

Latency budget the core metric

The total delay from your mouth closing to the agent's first audible word, broken down per stage. Humans expect a reply gap of a few hundred milliseconds; past ~1 second, conversation feels broken. Target: 600–900ms.

Example: see §8 below for the full breakdown. Key insight worth internalizing now: the biggest chunk (endpoint wait) is not computation at all — it's chosen silence, a UX decision about patience.

5. Architecture 1: browser ↔ server

The subtle dependency between ① and ②: the frontend contains this line, which decides which server the browser phones for the voice connection:

ws = new WebSocket(`${proto}://${location.host}/ws`);

Taking it apart piece by piece:

  • The backticks and ${...} — a JavaScript template literal: a string with blanks that get filled by live values. Pure string assembly: `hello ${name}!` becomes "hello world!" when name is "world". So the URL has two blanks to fill: proto and location.host.
  • proto — either "ws" or "wss" (the secure version). Think http vs https, but for WebSockets.
  • location.host — the important one. location is a built-in object the browser fills in describing the address of the page you're currently viewing; .host is the "where did this page come from" part (domain + port). The browser sets it — your code only reads it.

So the whole line means: "open a WebSocket back to the exact same place this page was served from, at the path /ws."

The two scenarios, concretely — same page, different ways of opening it:

How you opened the pagelocation.host becomesSocket URL becomesResult
Typed http://localhost:8000 (served from the server)localhost:8000ws://localhost:8000/ws✅ points at your server, which has /ws
Double-clicked the .html fileempty (it's a file:// path, no host)ws:///ws❌ no server there at all
Opened via a preview panel on another addresse.g. preview.local:3000ws://preview.local:3000/ws❌ that address has no /ws

That's the "load it from the server, not the file/preview" rule in one table. The page looks identical in all three cases — buttons render, layout is fine — but in the bottom two the socket is dialing a phone number where nobody is home. The app is deaf and mute: you hold the button and nothing reaches the pipeline.

Why build it this way anyway, instead of just hardcoding ws://localhost:8000/ws? Because that hardcoded string is only correct on your laptop, today. The moment the app runs anywhere else — a teammate's machine on a different port, or a deployed server at wss://interview-coach.yourdomain.com — the hardcoded value would be wrong and every connection would fail. Deriving from location.host says "connect back to wherever I came from," which is automatically correct in every environment with zero changes. The catch — and the reason for the whole warning — is that this only works if the page was genuinely served by the server in the first place; load it any other way and the "connect back to where I came from" logic faithfully connects you to the wrong place.

7. Architecture 3: anatomy of one turn

This is the step-1 app in one picture — what happened between you releasing the button and hearing the interviewer's next question. Time flows downward. (Kept in its original form because it's the clearest mental model of the cascade; Part II shows how every hop below has since evolved — the clip became a continuous stream, the reply became chunks, and the whole turn became cancellable.)

Why the text arrives before the audio (⑤ before ⑦): a small UX trick that costs nothing — the user can start reading the question during the ~1s TTS is still rendering, which makes the wait feel shorter. It also foreshadows streaming: the more of the pipeline's intermediate products you surface early, the faster the system feels, independent of how fast it is.

Why send the transcript back at all (③): trust. If the agent's next question seems off, the user can see whether STT misheard them. Voice UIs without visible transcripts feel haunted when recognition errors happen.

8. The latency budget

The one number that decides whether a voice agent feels like a conversation or a walkie-talkie: time from your mouth closing to the first sound of the reply. Human conversational gaps are ~200–400ms. Beyond ~1s, people start repeating themselves or checking if the app crashed. Target: 600–900ms.

Why our step 1 app is much slower than this chart: we don't stream, so stages can't overlap — each waits for the previous to completely finish. Whisper transcribes the full clip (1–2s), llama generates the full reply (2–4s), piper renders the full WAV (~1s): easily 4–7 seconds of silence per turn. That's not a bug — it's the baseline we'll measure (step 3's latency HUD) and then demolish, stage by stage. Feeling the difference is the point.

9. Component deep dive — what, why, how

frontend/index.html — the ears and mouth

WhatCaptures your mic, sends recordings up the socket, shows the conversation as text, plays reply audio.
WhyThe browser is the only sane cross-platform path to the microphone — and it ships professional-grade audio machinery for free (echo cancellation, format encoding). Even a "backend project" needs this thin web layer. It's deliberately frameworkless: one button and a log don't justify React, and every dependency added is noise between you and the concepts.
HowgetUserMedia obtains the mic stream once at start. Holding the talk button (or spacebar) runs MediaRecorder.start(); releasing runs .stop(), and the accumulated chunks are combined into one Blob and pushed down the WebSocket as a single binary frame. Incoming messages are sorted by type — strings parse as JSON (status/transcript/reply → rendered into the log), binary is audio (wrapped in an object URL, handed to an <audio> element).

The WebSocket protocol — the spinal cord

WhatOne persistent two-way connection at /ws carrying everything: setup JSON up, audio clips up, status/transcript/reply JSON down, reply audio down.
WhyConversation is inherently push-based — the server must be able to say things unprompted ("still thinking…", and later: partial transcripts, "stop, user interrupted"). HTTP can't do that. Adopting WebSocket on day one, before it's strictly necessary, means steps 3 and 4 change what flows through the pipe, never the pipe itself.
HowA fixed convention: text frames are JSON with a type field (setup, status, transcript, reply, error); binary frames are always audio. Typed control messages + raw media on one socket is exactly how production voice APIs (Deepgram, LiveKit) shape their protocols — you're learning the real pattern.

backend/main.py — the conductor

WhatOwns each conversation. Accepts the connection, holds the message history, and for every clip received runs the chain: transcribe → append to history → generate reply → synthesize → send back.
WhySomething has to hold state, because the LLM is stateless — it "remembers" the interview only because main.py re-sends the entire history each turn. Scoping that memory to the connection (one socket = one interview = one history list) is the simplest correct design. Note what main.py deliberately does not know: it never imports whisper, Ollama, or piper — it talks only to abstract interfaces.
HowAn async loop awaits frames. A setup text frame installs the system prompt (with your JD + resume baked in) and immediately triggers the interviewer's opening question. Each binary frame becomes one turn through _run_llm_tts. Status frames go out before each stage so the UI always knows what's happening.

backend/config.py + engines.py — the switchboard

Whatconfig.py reads flags (STT_ENGINE, LLM_ENGINE, TTS_ENGINE…) from .env. engines.py maps each flag to a concrete class, constructs it once, caches it, and hands it to anyone who asks.
WhyThis pair is the enforcement point of the adapter pattern. Because only the factory imports concrete engines, nothing else can accidentally depend on one — the swap-by-flag guarantee is structural, not aspirational. Caching matters because engines are expensive to create (whisper loads ~150MB of weights).
HowSimple if/elif on the flag with the import inside each branch — lazy importing, so the OpenAI SDK never even loads while you run local, and you don't need dormant engines' dependencies installed at all.

backend/stt/ — speech to text

Whatbase.py defines the interface (async transcribe(bytes) → str). local_whisper.py implements it with faster-whisper (active). deepgram.py implements it against Deepgram's API (dormant).
WhyLocal per your preference — free, private, offline. Whisper specifically because it's the open-source standard: whatever voice work you do after this project, you will meet Whisper again. The base model on CPU with int8 quantization is the accuracy/speed sweet spot for a laptop.
HowThe clip is written to a temp file so ffmpeg can sniff the container and decode Opus into raw samples; whisper then beam-searches (5 beams) over its acoustic model to find the best transcription. The call is wrapped in asyncio.to_thread because inference is blocking CPU work that would otherwise freeze the whole server. The model loads lazily on first use, then stays warm in memory.

backend/llm/ + prompts.py — the interviewer's brain

Whatbase.py defines reply(messages) → str plus a stream() that yields tokens. local_ollama.py talks to Ollama (active); openai_api.py talks to OpenAI (dormant). prompts.py builds the system prompt from your JD + resume.
WhyOllama because it makes local models trivial (one command, clean HTTP API) and llama3:8b was already on your machine. The prompt's odd-looking rules — short turns, one question, no markdown — exist because this text is destined for a speaker, not a screen: TTS reads formatting characters aloud, and nobody talks in bullet points. The stream() method is deliberately built now-but-unused: step 3 will need it, and writing the call streaming-capable today avoids a rewrite.
HowPlain HTTP POST to Ollama's local API (localhost:11434/api/chat) with the full message history; Ollama runs the model and returns the reply. The streaming variant reads Ollama's line-by-line JSON chunks and yields each token fragment as it arrives.

backend/tts/ — text to speech

13. Step 2: hands-free — VAD, endpointing, and the floor

Step 2 removed the button. That one sentence hides a complete change of architecture: instead of the browser sending one finished clip per turn, it now sends a continuous stream of raw audio for the entire interview, and the server must figure out — from sound alone — when a turn starts and when it ends.

The browser side: from MediaRecorder to AudioWorklet

AudioWorklet browser

A tiny JavaScript class the browser runs on its dedicated audio thread, handing it raw microphone samples every ~3 ms as plain Float32Arrays. It replaces MediaRecorder for us, because MediaRecorder produces compressed, containerized chunks (WebM/Opus) that only make sense as a complete file — useless when the server needs to inspect audio in 32 ms slices as it arrives.

Example from our code: our worklet (inlined in frontend/index.html as a Blob URL) just accumulates samples until it has ~2048, then posts them to the main thread, which downsamples them to 16 kHz, converts to 16-bit integers, and fires them down the WebSocket. No container, no codec — just numbers.
WhatThe mic streams raw PCM — 16 kHz, mono, 16-bit signed little-endian — over the WebSocket, continuously, from "Start interview" until the end. There is no per-turn client logic at all anymore: the browser doesn't know when your turn starts or ends. The server decides.
Why raw PCM, and why this exact format? Because both consumers on the server — Silero VAD and whisper — natively want 16 kHz mono float arrays. Sending exactly that (as int16, 2 bytes/sample ≈ 32 KB/s — trivial on localhost) means the server does zero decoding: it reinterprets bytes as samples and goes. The step-1 path needed ffmpeg to unpack WebM/Opus; that entire dependency fell away. Fixing the wire format in config (SAMPLE_RATE=16000) is a contract, and contracts beat negotiation for learning projects.
HowThe mic hardware usually runs at 48 kHz, so the main thread linearly interpolates down to 16 kHz (downsample()), clamps floats to [-1, 1] and scales to int16 (toInt16()). One subtlety: we create the capture AudioContext asking for 16 kHz directly (new AudioContext({sampleRate: 16000})) — most browsers oblige, and the downsampler is the fallback when hardware refuses.

The server side: frames → probabilities → decisions

WhatWebSocket bytes are appended to a residual buffer and cut into exact 1024-byte frames (512 samples × 2 bytes = 32 ms). Every frame gets a speech probability from Silero VAD; the Endpointer folds that probability stream into turn-level events; on END the buffered frames are joined into one utterance and handed to the pipeline — the same STT→LLM→TTS flow as step 1.
Why a residual buffer? Because the network doesn't respect frame boundaries — a WebSocket message might carry 2048 samples or 1500. Silero requires exactly 512-sample frames at 16 kHz. The framer decouples "how bytes arrive" from "what the model needs" — a two-line pattern (while len(buf) >= FRAME: cut) you'll reuse in every streaming system you ever build.
How_process_frame in backend/main.py: reinterpret 1024 bytes as int16 → float32 in [-1,1] → vad.speech_prob(frame) → endpointer.update(prob) → act on the event. Silero runs as a tiny ONNX model — sub-millisecond per frame on CPU, which is what makes "score everything, always" affordable.

Preroll ring buffer the detail everyone forgets

VAD always fires a beat late — it needs a few frames of evidence before it's confident. If you start the utterance at the trigger frame, the first phoneme is missing and STT hears "…orked at Google" instead of "I worked at Google". The fix: always keep the last few frames in a small ring buffer (collections.deque(maxlen=5) ≈ 160 ms), and when speech starts, seed the utterance with them.

Example: you say "So…" — VAD confirms speech at frame 3, but frames 1–2 (the "S" sound) are already gone from the live stream. The preroll ring still has them; the utterance starts complete. Cost: 10 KB of memory. This trick returns in step 4's barge-in fix (§15), in a different costume.

14. Step 3: streaming — first sound in half the time

Step 2's hands-free loop still had step 1's core sin: every stage waits for the previous to fully finish. Whisper finishes the whole transcript, llama writes the whole reply, piper renders the whole WAV — and only then do you hear anything. Step 3 attacks the silence with the single biggest latency lever in voice AI: overlap.

The hinge: cutting a token stream into speakable chunks

Whatbackend/text_chunking.py — an async generator that consumes LLM tokens and yields the earliest complete-sounding piece of text: for the very first chunk, anything past 18 characters ending in a comma; after that, whole sentences.
Why clauses and not fixed sizes? Because TTS quality dies at bad seams. Cut every 20 characters and piper pronounces half-words with wrong intonation; wait for full sentences always and you lose the latency win on long first sentences. The compromise encodes something true about speech: a comma is a place a human would breathe. And the first-chunk-is-special rule exists because time-to-first-audio is the only number the user feels — "Thanks for sharing that," can be speaking while the rest of the sentence is still being generated.
HowBuffer tokens; scan for the earliest sentence-ender (. ! ?) — or, for the first chunk only, a clause-ender (, ; :) past the minimum. One hard-won refinement (found in review, §15's sibling): an ender only counts if followed by whitespace — otherwise "3.5" splits into "3." + "5" and "Node.js" gets spoken as two fragments. Punctuation at the very end of the buffer waits for the next token to prove it's a real boundary; the stream-end flush catches final periods.
# the shape of a streamed turn (main.py, simplified)
async for chunk in speakable_chunks(llm_tokens):
    send_json("reply_delta", chunk)      # text appears in the UI now
    wav = await tts.synthesize(chunk)    # small text = fast synth
    send_bytes(wav)                      # browser plays chunk 1
                                         # …while the LLM writes chunk 3

The browser side: gapless playback on the Web Audio clock

WhatEach arriving WAV chunk is decoded and scheduled to start at the exact sample the previous chunk ends — so five separate files play as one seamless voice.
Why not just play each chunk as it arrives? Two failure modes. Play-on-arrival stutters: network jitter puts 50 ms gaps between chunks, and human ears are merciless about gaps inside a sentence. And decoding is async — chunk 2 can finish decoding before chunk 1, so naive code plays them out of order. The Web Audio API exists for exactly this: it has its own high-precision clock and lets you book playback in the future, sample-accurately.
HowdecodeAudioData → schedule at max(now, nextStartTime) → advance nextStartTime += buf.duration. Ordering is forced by chaining every decode onto one promise chain (scheduleChain), so chunks schedule strictly in arrival order regardless of decode speed. Note there are two AudioContexts: capture runs at 16 kHz (the wire contract), playback at the device's native rate (piper's audio is 22 kHz and forcing it through a 16 kHz context would resample it down — audibly worse).
const startAt = Math.max(playCtx.currentTime, nextStartTime);
src.start(startAt);                       // booked on the audio clock
nextStartTime = startAt + buf.duration;   // next chunk butts up exactly
The HUD — making latency a first-class citizen Every turn, the server sends a metrics frame: stt_ms (utterance end → transcript), text_ms (→ first speakable chunk), audio_ms (→ first WAV sent — the number that matters). The UI shows them after each turn (now inside the collapsible developer panel, §18). Why bother? Because you can't grind down a number you can't see — the HUD is what turned "feels sluggish" into "STT is 80% of the remaining wait, whisper-base is the next target". Measurement before optimization, always.

15. Step 4: barge-in — and the two best bugs of the project

Interrupting a human mid-sentence works because they hear you while talking, stop fast, and cede the floor. Making software do that decomposed into four requirements, each mapping to one mechanism:

RequirementMechanism
Hear the user while speakingThe mic never stops sending — the step-2 gate ("ignore audio unless LISTENING") became a router: while a turn is active, frames go to barge-in detection instead of the endpointer.
Don't hear yourselfBrowser echo cancellation (echoCancellation: true) subtracts the reply audio from the mic signal. Headphones make it near-perfect; on speakers, residual leak is why detection must be strict.
Be interruptible at allEach turn runs as its own cancellable asyncio task — the receive loop stays free to hear you (the §3 event-loop lesson paying off exactly as promised).
Stop everything, instantlyCancel the task server-side; send interrupt; the browser kills all scheduled audio and drops in-flight chunks.

asyncio.Task and cancellation python async

asyncio.create_task(coro) starts a coroutine running concurrently on the event loop and returns a handle. task.cancel() makes CancelledError erupt inside the task at its current await point — a cooperative "stop now" that the task can catch to clean up. This is the idiomatic asyncio way to make long work abortable.

Example from our code: _start_turn spawns _turn_wrapper(pcm) as a task and returns immediately — so the receive loop keeps consuming mic frames during the whole 5-second turn. Barge-in is then just task.cancel(): the error surfaces inside _run_turn wherever it happens to be — mid-LLM-stream, mid-TTS, or in the playback sleep — and generation stops within milliseconds.
WhatDetection: while a turn is active, a frame counts toward barge-in if its speech probability ≥ 0.6, and the interrupt fires only after ~240 ms of consecutive such frames. Trigger: cancel the turn task, send {"type":"interrupt"}, hand the floor back, and replay the trigger frames (below).
Why stricter than normal VAD (0.6 vs 0.5), and why sustained? Because the cost of a false positive is horrible: the interviewer cuts itself off mid-question for no reason. During playback the mic signal contains echo-cancellation residue — brief, low-confidence "speech-ish" flickers. A higher bar plus a required run length means a cough or a leaked syllable does nothing, while real speech (which sustains effortlessly) still interrupts in a quarter second. Two thresholds for two different costs of being wrong.
HowClient side, stopAllAudio() stops every scheduled source and — the subtle part — bumps an epoch counter (interruptedAt). Chunks still in the decode pipeline carry the old epoch and silently no-op when they surface. Without the epoch, a chunk that was mid-decode during the interrupt would schedule itself after the flush and blurt a fragment of the dead reply.

War story #1: the turn that wouldn't die

The bug, as experienced Barge-in passed its tests… and then in a real interview: you interrupt, the AI transcribes what you said — but finishes its whole sentence first, then answers the interruption as the next turn. Detection clearly worked. So what was off?

The diagnosis: two clocks. The server finishes sending a reply's audio in ~2s (synthesis + network). The browser takes ~6s to play it, because playback runs at the speed of speech. The server considered the turn over when it finished sending — so for those last 4 seconds, it was back in LISTENING mode: your interruption didn't hit the barge-in path at all. It hit the endpointer, and was dutifully captured as the next turn while the browser (knowing nothing) kept playing.

The fix (in _run_turn): as each WAV chunk goes out, read its real duration from the header (_wav_seconds) and accumulate. After generating, don't release the floor — sleep out the remaining playback time:

remaining = audio_secs - (time.perf_counter() - first_audio_at)
if remaining > 0:
    await asyncio.sleep(remaining)   # still SPEAKING; still watching for barge-in
                                     # and cancellable — an interrupt cuts it short

The lesson, worth generalizing: in any streaming system, "I finished producing X" and "the consumer finished consuming X" are different events, and confusing them creates windows where your state machine believes something false about the world.

War story #2: the interrupt that erased your answer

The bug History was appended only after the generation loop completed. Interrupt during playback? Fine — appends had already run. Interrupt during generation (early, before or during the first chunks)? The cancel landed before the appends: your transcribed answer and the partial reply simply vanished from messages. Next question ignored what you'd just said, and the debrief under-counted your answers. Classic cancellation bug: CancelledError can erupt at any await, and any bookkeeping that lives "after the loop" silently becomes optional.

The fix: a record_turn() closure with a once-guard, called from both the normal completion path and an except asyncio.CancelledError handler (which re-raises after recording). Whichever path runs first wins; the other becomes a no-op. Interrupted replies get an explicit marker appended — [cut off by the candidate] — so both the interviewer LLM and the debrief evaluator know that line was never fully delivered.

Why not just append the user message as soon as the transcript arrives? The obvious fix is wrong in a subtle way, and it's worth understanding why: the cascaded strategy yields the Transcript event first, and only afterwards builds its LLM context as history + [user message]. If the transcript callback appended to history immediately, the user's answer would appear twice in the LLM's context. Ownership matters: the strategy owns "context for this turn", the session owns "history of committed turns" — the fix respects the boundary, the obvious fix violates it.

Two refinements found in review

The first word of your interruption survives. The ~240 ms of speech that triggers barge-in used to be discarded — buffers were cleared on floor handback, so your interruption was captured only from re-detection onward, often missing its first word. Now those trigger frames are buffered and, after the floor returns, replayed through the normal frame path: VAD sees them, START fires, the utterance is seeded. It's the preroll idea (§13) again — same insight, new location: the evidence that made you act is usually also data you need to keep.

Mute sends silence, not nothing. The endpointer is driven by incoming frames; if muting simply stopped sending, a half-captured utterance would freeze mid-turn until unmute. Instead the browser keeps sending frames while muted — zeroed. The server hears "silence", the endpointer counts it, the turn ends normally. In stream protocols, "no data" and "data that says nothing" are very different messages.

16. Cascaded vs fused: the Gemma 4 experiment

Everything so far assumed the cascade: separate STT and LLM models. But a new class of natively multimodal models can consume raw audio directly — one model both hears and thinks. We added Google's Gemma 4 (E4B, Apache-2.0, runs locally via transformers) as a complete alternative pipeline, switchable with one flag: PIPELINE=cascaded|fused.

WhatA second layer of the adapter idea, one level up: TurnStrategy (backend/pipeline/base.py) abstracts how a whole turn is processed — run(utterance_pcm, history) yields Transcript then ReplyToken events. CascadedStrategy = whisper + Ollama. FusedStrategy = Gemma 4 for both jobs. main.py consumes the event stream and does everything shared: chunking, TTS, HUD, history.
Why abstract at the turn level and not just swap the STT engine? Because fused isn't an STT engine — it collapses two stages into one call, so the seam between them disappears. The engine-level adapters (§6) can't express that; the strategy level can. This is also the dress rehearsal for step 6: a realtime speech-to-speech model is "just" a third strategy.
HowThe events are tiny dataclasses; the strategy is an async generator. Everything downstream of the events — speakable chunks, piper, the metrics — is identical for both pipelines, which is what makes the comparison honest.

What the experiment taught (three findings, all earned the hard way)

Finding 1 — device_map="auto" silently paid a disk tax First fused runs took 12.45s per reply. The cause hid in one log line: "Some parameters are on the meta device…" — transformers' device_map="auto" had mis-judged available memory and offloaded some layers to disk, despite 36 GB of RAM. Every forward pass paged weights back in. Explicitly detecting and pinning the device (mps) in pipeline/fused.py dropped it to 4.78s — over half the latency was one silent default. Lesson: "auto" placement is a guess, and guesses about memory deserve verification when latency matters.
Finding 2 — one call per job, not one call for two jobs The elegant design was a single Gemma call returning "transcript\nreply". Gemma followed that format only about half the time — and when it didn't, the parser mis-split, instruction text leaked into the visible transcript, got committed to history, and poisoned every later turn (the interviewer drifted into fabricated questions). The fix: two clean calls — call ① transcribe only (greedy decoding, nothing else in the output), call ② reply only, from history + transcript. Costs a second inference; buys deterministic parsing. Lesson: parsing a model's free-form compliance is a tax you pay on every single turn — restructure so there's nothing to parse.
Finding 3 — warm up at boot, not on the first victim The first fused turn took ~10s even after the device fix: model loading + MPS kernel compilation happen on first inference. Moved to a FastAPI lifespan hook: at server start, the pipeline's warmup() loads weights and runs a tiny text + audio generation to compile the kernels (~11s, once, while nobody's waiting). First user turn: ~5s. Cascaded's warmup is a no-op — the abstraction lets each strategy define what "ready" means.

17. Step 5: the scored debrief — the LLM as judge

Until step 5, ending the interview just… stopped the audio. The debrief turns the transcript into feedback — and introduces a genuinely different discipline of LLM use: the model as evaluator instead of conversationalist.

Design decision zero: two signals, kept separate on purpose

WhatThe debrief combines delivery metrics — pure arithmetic on data captured during the interview (words-per-minute, filler-word rate, average answer length, talk-time ratio) — with rubric scores — the LLM's judgment of answer content across four behavioral dimensions (Structure, Specificity, Ownership & impact, Communication), plus strengths and improvements.
Why not let the LLM report the numbers too? Trust, and its failure modes. An LLM asked "how many filler words?" will produce a plausible number, not a counted one. Keeping the two channels separate means every number on the screen is true by construction (the UI even says "computed directly from your speech — not a model's guess"), and the model's opinions are clearly labeled as opinions. When a scoring hallucination happens — and eventually one will — it can't contaminate the metrics.
HowDuring the interview, main.py accumulates turn_stats per answer (word count, speaking seconds, text) and total AI airtime. Speaking seconds are the utterance's PCM length minus the capture overhead (preroll + 700 ms endpoint silence — not talking, just machinery), so WPM isn't quietly deflated. AI airtime counts only audio that actually played — a barged-in reply contributes its heard portion, not its synthesized length. Fillers are counted with word-boundary regexes (so "like" doesn't fire inside "unlikely") including multi-word fillers ("you know", "kind of").

LLM-as-judge / rubric prompting llm discipline

Using a model to evaluate text against explicit criteria rather than to converse. The craft is entirely different from the interviewer prompt: you pin the dimensions (so it can't invent its own), pin the scale (1–5, with meaning anchored), demand evidence ("must reference the transcript"), forbid invention, and — critically — demand machine-readable output and nothing else.

Example from our rubric prompt (backend/debrief.py): "Base every judgement on what the candidate ACTUALLY said"; "If the interview is very short or the candidate gave non-answers, score low and say so"; "Improvements must be actionable ('quantify your results', not 'be better')"; then an exact JSON shape to fill. Same anti-fabrication battle we fought in the interviewer prompt (§16, finding 2) — evaluators hallucinate praise as readily as interviewers hallucinate questions.

War story #3: the JSON that was missing one brace

The bug llama3:8b produced excellent, well-formed rubric JSON… minus the final }, reliably. json.loads failed, the code fell back to metrics-only, and the entire scored review silently vanished — no error, just an inexplicably empty debrief. Small local models are much better at starting structure than finishing it.

The fix: a repairing extractor. Walk the text once, tracking bracket depth while correctly ignoring everything inside string literals (including escapes), then append whatever closers (}, ], ") are still open, and parse again. The general shape of the lesson: when a model produces structured output, your parser is part of the model's error distribution — design it for the model you have, not the model you wish you had. Two supporting details: the scoring call passes max_tokens=700 (a new per-call override on the LLM interface — the interviewer's 80-token cap that keeps spoken turns snappy would strangle a full review), and generate_debrief() is written to never raise: any failure degrades to metrics-plus-a-note, because a broken review must not eat the interview.

What (the end-to-end flow)You click End interview → the browser stops the mic and playback but keeps the WebSocket open → sends {"type":"debrief"} → the server cancels any in-flight turn (so the transcript can't mutate mid-scoring), computes metrics, runs the judge, sends one payload → the debrief screen renders.
Why keep the socket open — and why cancel the in-flight turn? The socket is the session: closing it would discard the server-side history before it could be scored. And scoring a transcript while a turn task is still appending to it is a race — cancel first, then read. Both are instances of the same rule: define the object's final state before you analyze it.
How (the failure paths)Three independent guards make the "Scoring your interview…" spinner un-hangable: a server error frame routes to the failure renderer while a debrief is pending; a WebSocket close does the same ("connection lost"); a 90-second client-side watchdog catches a silently hung server. All three land on the degraded screen — headline with the reason, metrics if available, transcript export always. (This was review bug #2 — the original code could spin forever with the error painted onto a hidden view.)

18. The frontend: from scratch page to interview platform

The original frontend was a debugging scratchpad: two textareas, a button, a log. It's now a three-view product — and the redesign is itself a lesson: every piece of invisible pipeline state became something you can see, which changes debugging from log-archaeology into watching a dashboard.

WhatThree views in one file, no framework, no build step. Lobby: candidate name/role, JD + resume, interview-type picker, difficulty and length, a live mic check. Live stage: timer, question counter, connection chip, interviewer presence avatar, live mic meter, mute, end button, chat-style transcript, and a collapsible developer panel (the §14 HUD plus floor state, VAD state, frames sent, turn count). Debrief: §17's payload rendered — overall badge, rubric bars, strengths/improvements, metrics grid, transcript export.
Why does a learning project need a "real" UI? Three honest reasons. Practicing the scenario end-to-end matters — a mock interview should feel like an interview, or you won't rehearse seriously. The state displays double as instruments: when barge-in misbehaves, the floor/VAD readouts in the dev panel show you what the server believes, live — that's how war story #1 was understood. And features that don't exist say "Coming Soon" instead of pretending: for months the type picker offered Technical/Coding/System-design as visibly disabled, because the prompt (§3, system prompt) only implemented behavioral. An honest UI is documentation — and when §19's interview packs made those rounds real, un-disabling the cards was the changelog. (Recording and video still wear the badge, truthfully.)
How (three details worth stealing) The mic check runs an AnalyserNode over its own temporary stream and animates an RMS level bar — users confirm the mic works before the interview, killing the most common "it's broken" report; the stream is released before the real capture starts. The presence avatar is driven purely by the server's state/vad frames (blue ring while SPEAKING, green while you talk) — zero client-side guessing, so it's also a truthful floor-state debugger. The lobby fields (name, role, type, difficulty) are folded into a preface on the JD text in the setup message — the server's contract didn't change at all, which is the adapter mindset applied to a protocol.
Where the project stands, and what's next Steps 1–5 are built, reviewed, and bug-fixed; the fused pipeline is a working bonus experiment. Two threads remain. Step 6 — swapping the cascade for a realtime speech-to-speech model — is the capstone the TurnStrategy abstraction (§16) was built to receive. 19. Interview packs: one interviewer, many rounds

Until now, every prompt in the project was hardcoded behavioral: the spoken persona said "behavioral interviewer", the director judged answers by STAR-story rules, and the debrief scored Structure/Specificity/Ownership/Communication no matter what you were practicing for. The lobby collected an interview type — and then threw it into a text preface the prompts mostly ignored. This section made topic and company first-class: pick DSA, Machine Learning, System Design, or Behavioral, optionally target a company bar (OpenAI · Anthropic · Google · Meta), and the persona, the director's judgment, and the debrief rubric all swap together.

WhatTwo small registries and a composition function. backend/packs.py defines one InterviewPack per topic, each contributing four things: a persona (the domain half of the system prompt — what to probe, what a good answer looks like), director guidance (what counts as evidence vs. a red flag in this domain), an opening move, and a four-axis rubric for the debrief. backend/companies.py adds a signal profile per company — one honest paragraph on what that bar actually screens for (first-principles reasoning at OpenAI, intellectual honesty about uncertainty at Anthropic, rigor-at-scale at Google, impact-and-shipping at Meta; generic injects nothing). prompts.py composes: shared spoken rules + pack persona + company signal + difficulty block + pack opening + JD/resume.
Why this shape — the real lessonThis is prompt composition as separation of concerns. The rules about brevity, one-question-per-turn, and never inventing specifics aren't behavioral-interview rules — they're properties of the medium (a live voice call), so they moved into a shared block every pack inherits. The domain knowledge is what varies, so it lives in the pack. The company overlay is a third, orthogonal axis. Without this split you get four near-duplicate mega-prompts that drift apart with every edit; with it, prompts.py and debrief.py stay generic plumbing and a new round type is ~40 lines of registry entry. It's §6's adapter pattern applied to prompts instead of engines.
How it threads throughThe lobby's four (now all-enabled) type cards plus a company dropdown ride the existing setup frame. main.py passes them to build_system_prompt() and stamps them onto DirectorState — so the director loop's signature and action schema never changed; the topic rides the state object it already owned. The debrief pulls its rubric from the pack, so a system-design round is scored on Requirements & scoping / High-level design / Trade-offs & bottlenecks / Communication, not STAR structure. Unknown type or company? get_pack()/get_company() fall back to behavioral/generic — never raise, matching the harness's degrade-don't-break rule everywhere else.

The constraint that shaped the design: don't touch the schema built — reliability

The tempting version of this feature gives each topic its own director actions (note_complexity, note_scoping…). We deliberately didn't. The director's five-action flat schema (§21's centerpiece) stays byte-for-byte identical across every topic — only the judgment text around it changes ("a red flag here means a wrong complexity claim" vs. "blame-shifting onto the team"). Two reasons: schema→grammar compilation for constrained decoding is the fragile step with a small local model, and a schema that never changes means every downstream consumer (the UI's director log, the debrief's notes block, the eval judge) keeps working untouched. Vary the prompt, freeze the contract.

Verified live, not vibed (rule 5): fed the DSA/Google director a candidate who described a correct hash-map approach for two-sum but never stated complexity. It chose note_evidence ("correctly proposed a hash map…") then probe_deeper ("ask for the time complexity — they didn't mention it"). The domain guidance demonstrably reaches the model's judgment, through the unchanged schema.
One more medium-shaped rule A voice DSA round has a failure mode a text one doesn't: the model asking you to "write a function". Every technical pack states spoken only — never ask them to write, type, or diagram, and the shared rules repeat it, because a local 8B model needs the constraint twice. This is the same lesson as the brevity rules: the medium (voice) imposes requirements no amount of domain prompting implies.

The centerpiece: from chatbot to agent

Today the interviewer is one LLM call per turn: history in, words out. The plan is to make each turn a small agent loop — the model chooses structured actions, a hand-rolled harness validates and executes them, and only one action (speak) actually produces voice.

Tool use / function calling planned — agent core

Instead of free text, the model emits a structured call — {"action": "probe_deeper", "reason": "no metric given"} — chosen from a menu of tools you define with typed schemas. The model proposes; your code validates and executes; the result goes back into the context and the model chooses again. That proposal→validation→execution→feedback cycle is the agent loop — everything else (frameworks, MCP, "agentic AI") is packaging around it.

Planned action menu: note_evidence (log what the answer proved — becomes the debrief's input), probe_deeper, switch_topic, flag_red_flag, end_interview, and speak (the only one the candidate hears). A turn may chain a few: note_evidence → probe_deeper → speak.

Constrained decoding / structured outputs planned — reliability

Rather than asking the model for JSON and repairing what comes back (§17's missing brace), constrained decoding masks the model's token choices during generation so that only schema-valid output is possible. Ollama exposes this as a format parameter carrying a JSON schema.

Why it matters here: an agent loop multiplies structured-output calls (every action, every turn) — so parse failures stop being an occasional debrief nuisance and become a per-turn tax. Making invalid output impossible beats making the parser cleverer. It will also retire §17's brace-repair hack — the right fix for a bug we've already met.

Agent harness planned — the part you write

Everything around the model that makes tool use safe and useful: the loop itself, schema validation, bounded retries on bad output, an iteration cap (so a confused model can't spin forever), and the state that lives outside the model — here, an evidence notebook, topic-coverage tracker, and red-flag list that persist across turns and don't depend on the model's memory.

Why state-outside-the-model is the big idea: today the debrief re-reads the whole raw transcript and judges it in one shot. With the director, the debrief reads the evidence notebook the agent itself maintained — structured, accumulated judgment instead of one giant retrospective glance. Same lesson as §17's metrics: move what can be structured out of the model's head.
